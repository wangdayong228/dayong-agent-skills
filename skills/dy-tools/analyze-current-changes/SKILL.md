# Analyze Current Changes

## 目标

输出一份中文“当前修改介绍”，支持三种输出模式：

- `brief`：简短结果，适合快速同步
- `standard`：一句话总结 + 背景 + 逐项说明
- `detailed`：标准版 + 更细粒度代码定位与风险说明

## 适用场景

当用户提出以下诉求时使用本技能：

- “分析我当前修改”
- “给我写变更介绍/改动说明”
- “总结这次改动做了什么”
- “按文件解释这些 diff”
- “写 release note/PR 描述草稿（基于本地改动）”

## 模式选择规则

优先级：用户显式要求 > 上下文推断 > 默认值

1. 选择 `brief` 的触发词
   - “简短”
   - “一句话”
   - “3 点以内”
   - “快速同步”

2. 选择 `standard` 的触发词
   - “介绍背景”
   - “写个说明”
   - “PR 描述”
   - “给团队同步”

3. 选择 `detailed` 的触发词
   - “详细分析”
   - “逐项说明”
   - “逐文件/逐模块”
   - “带代码定位”

4. 未明确时默认 `standard`
   - 并在结尾补一句：可按需切换为 `brief` 或 `detailed`

## 输入边界

- 只基于当前工作区可见改动（staged + unstaged + untracked）。
- 不假设未展示的业务背景；未知信息明确标注“待确认”。
- 不编造测试结果、性能收益、链上效果或上线状态。

## 分析流程

按顺序执行：

1. 收集改动范围
   - 查看工作树状态
   - 区分：新增/修改/删除、核心逻辑/工具脚本/配置文档

2. 建立改动主题
   - 按“功能主题”聚合文件，而非只按文件名罗列
   - 每个主题要有可解释的业务意图

3. 提炼因果关系
   - 每个主题回答三件事：
     - 为什么要改（动机/问题）
     - 改了什么（机制/结构）
     - 影响什么（行为/风险/兼容性）

4. 生成代码定位
   - `standard`/`detailed` 下，每个主题都必须内嵌代码定位
   - 每个主题至少给 1 个定位点
   - 优先定位到函数/方法/结构体，其次文件级说明
   - 需要代码介绍时，附最小必要片段

5. 生成最终文案
   - 按当前模式对应模板输出
   - 保持可直接复用到 PR、周报、交接文档

## 输出模板

### 模式 A：brief

1. 一句话总结  
2. 关键点（最多 3 条）  
3. 可选：1 条风险提示

### 模式 B：standard

1. 一句话总结  
2. 背景介绍（叙述式：问题来源 → 约束 → 本次策略，2-3 段，面向人阅读）  
3. 逐项说明（每项必须含：主题/动机/实现/影响/代码定位）  

### 模式 C：detailed

1. 一句话总结  
2. 背景介绍（叙述式：问题来源 → 约束 → 本次策略，2-3 段，面向人阅读）  
3. 逐项说明（每项必须含：主题/动机/实现/影响/代码定位/必要片段）  
4. 整体影响评估（不逐项复述：正向收益 + 代价/取舍，收束成 1-2 段）  
5. 风险与验证建议（按优先级 P0/P1 叙述，不写成机械勾选清单）  

## 输出呈现规范（强制）

- 必须使用清晰标题层级：`##`（主段）+ `###`（子段）；禁止整篇无层级平铺。
- 默认骨架固定为：`一句话总结` → `背景` → `关键改动（按主题）` → `整体影响` → `验证建议`。
- 背景仅 2 段：第一段讲“原问题与后果”，第二段讲“本次策略与边界”。
- `standard`/`detailed` 中，每个主题最多 6 行（动机/实现/影响/文件/符号/代码片段），禁止超长条目。
- 代码片段只保留最小必要上下文，建议 3-6 行；禁止大段粘贴导致喧宾夺主。
- 禁止同义重复：`逐项说明` 已说过的信息，不在 `整体影响` 与 `风险` 中重复展开。
- 文风要求“自然说明文”，避免审计日志腔、流水账腔和过度术语堆叠。

## 逐项说明内嵌格式（standard/detailed）

`standard` 和 `detailed` 每个主题都按以下格式输出，不再拆分独立“代码定位”章节：

- `<主题名>`
  - 动机：<为何改>
  - 实现：<具体改动机制>
  - 影响：<行为变化、兼容性、潜在风险>
  - 文件：`path/to/file`
  - 关键符号：`FuncName` / `TypeName.Method`
  - 代码片段：（detailed 必填，3-6 行最小必要上下文）

## 写作要求

- 始终使用中文。
- 先结论后细节，避免流水账。
- 禁止空泛表述（如“优化了代码质量”），必须对应到可定位改动。
- `standard`/`detailed` 下，逐项说明与代码定位必须合并输出，保证读者可边读边跳转。
- 不输出与当前改动无关的历史信息。
- 改动较多时按“功能主题”组织，不按文件机械罗列。

### 非逐项部分（背景/整体影响评估/风险）写作风格

- 这些部分面向人阅读，用连贯的叙述段落，不要退化成表格堆砌或工程日志式条目。
- 背景介绍走“问题来源 → 约束 → 本次策略”三段式，把改动放进上下文，而不是罗列文件。
- 整体影响评估要收束成 1-2 段结论（收益与代价的权衡），不逐项复述逐项说明。
- 风险与验证建议按 P0/P1 优先级组织，用一句话说清“验证什么、怎么验证”，避免无优先级的勾选清单。
- 背景、整体影响、风险三部分的句子应能顺读成文，避免“关键词堆叠式短句”。

## 质量检查清单

输出前自检：

- [ ] 已按规则选定模式（brief/standard/detailed）
- [ ] 已给出一句话总结
- [ ] 使用了清晰标题层级（`##` + `###`）
- [ ] `standard`/`detailed` 的背景介绍是叙述式三段（问题→约束→策略），非表格/日志堆砌
- [ ] `standard`/`detailed` 的每个主题均包含动机/实现/影响/代码定位
- [ ] `standard`/`detailed` 的每个主题不超过 6 行
- [ ] `detailed` 的每个主题均包含必要代码片段
- [ ] 代码片段为 3-6 行最小上下文，未大段粘贴
- [ ] `detailed` 含“整体影响评估”收束段，且未逐项复述
- [ ] `detailed` 的风险与验证建议按 P0/P1 优先级叙述
- [ ] 背景/整体影响/风险三部分读感自然，无机械日志腔
- [ ] 不确定信息明确标注“待确认”
- [ ] 全程中文，可直接复用
