# 请求幂等

适用于以幂等键识别重复写请求的接口。**同一操作重试沿用 key，新操作使用新 key；请求幂等不能替代业务防重。**

## 基本规则

- 沿用项目对 key 位置、生成方、作用域、保留期及处理中、成功、失败响应的约定；仅确认未决项。
- 调用方须在首次执行前取得并保存 key。重试保持 key 和参数不变；key 不等同于请求追踪 ID。
- 每次请求均须鉴权，包括重放。key 按约定的租户、调用方或操作范围隔离，禁止跨调用方泄露结果。
- 请求匹配包含操作、目标资源及全部业务参数，不依赖资源当前状态。按接口语义规范化后比较或生成摘要，排除 key、追踪 ID；忽略 JSON 空白和字段顺序，但不能擅自忽略数组顺序、缺失值与零值的差异。

## 请求处理

鉴权后先查幂等记录，再决定是否执行业务；避免原操作造成的状态变化阻断合法重放。

| 情况 | 处理 |
| --- | --- |
| 新 key | 业务校验通过后受理并绑定请求、结果 |
| 同 key、同参数，已受理 | 返回原受理结果，不重复写入 |
| 同 key、同参数，仍在处理 | 按约定等待或返回处理中，不重复执行 |
| 同 key、不同参数 | 报参数冲突，保留原记录 |
| 不同 key、相同参数 | 按新操作校验唯一性、余额、占位等业务约束 |

重放返回原受理结果，异步进度另行查询。例如 K 将名称改为 X，后来新请求改为 Y；K 重放仍返回原结果，不能写回 X，也不能用 Y 替代原结果。

## 保存与并发

- 用持久化唯一约束或等效机制保证作用域内的 key 只绑定一次；内存标记、先查后写或短时缓存锁不足以保证幂等。
- 幂等记录、业务写入及重放结果须原子提交，或提供等效恢复保证：崩溃后仍能定位原操作，恢复期间不会重复写入。事后补记录本身不够。
- 提交结果未知时沿原 key 核实。明确受理前失败是否绑定 key、受理后失败如何重放或恢复；不能把错误当成未执行，也不能仅因超时删除或抢占处理中的记录。

## 外部调用与过期

本地事务不覆盖外部操作。发送前持久化上游业务标识和 key，保持与本地操作的稳定映射；重试核对上游去重范围、有效期及参数约束。结果未知或幂等过期时先核对原操作；无可靠去重或恢复保证，不自动重发。任务恢复与取消见 `durable-async-task-lifecycle`。

记录保留期须覆盖承诺的重试窗口。仅在原操作结果明确、关联任务不再依赖记录时清理；不得删除处理中或结果未知的记录。明确过期 key 的行为：删除记录可能导致旧请求重新执行；仍需拒绝旧 key 时，保留已用标记或等效识别机制。

## 验证

覆盖同 key 并发、参数冲突、调用方隔离、不同 key 的业务冲突、响应丢失、提交结果未知、资源后续修改及记录过期。验证不重复执行、不越权泄露、重放原结果且不覆盖新值；涉及外部系统时验证不会重复提交。
